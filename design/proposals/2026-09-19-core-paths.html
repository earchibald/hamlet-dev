Where the core goes next

You asked whether Hearth should stay a web product, and whether the core should move to a faster typed language. You also asked what should change in the model as the world grows. The answers are in the first table. The rest is the evidence: measurements from dev, and sources that are numbered and listed at the end.

The answer

Stay a web product?Yes. Keep the single HTML file as the release. Add a desktop build later as a second front end.Every game engine we looked at, Godot included, gives up the single file and the Node tests. Nothing we measured needs one.

Current features are treated as essential but not sacred. Where an option would change a written rule of the project, it says so. The two steps that would need the golden blessed again say so as well.

Three quarters of the time goes to the beings, and much of that is path search

Two agents profiled the same run on dev: seed r, the default world, no page, Node only. One used node --cpu-prof for 70 game days. The other used node --prof for 40.

Both ran on an Apple M5 Max while other sessions ran soaks. The load average was about 10, which means about ten jobs wanted a processor at any moment. Shares of time and ratios hold up under that. Absolute times do not. Where this page gives one, it says so.

The average tick follows the people. The worst tick follows the map, in the one case we measured.

The area will grow, and so will the number of beings. The number of ticks grows most: plan G4 moves a day from 1,000 ticks to 86,400. The G spec sets a budget of one world day in under 5 seconds in Node. That is about 58 microseconds a tick.

Eight small fixes come first, and six should leave the golden alone

None of these needs a new language or a new structure. Each one is a task or two. One term first: a typed array is a fixed block of plain numbers, such as Int32Array, and it is smaller and faster to read than a list of objects. Six changes to the model, in the order we would make them

1. Type checks on the JavaScript we have

TypeScript can check plain .js files. It reads the types from JSDoc comments, which are notes above a function that name each argument's type. There is no build step and no output. It treats files that share one scope as scripts, which is what src/sim/ is. It would catch wrong argument counts, misspelt fields, and a tile field that one file adds and another never expects. It breaks no project rule. Note that TypeScript 7 is faster at checking only. It does not make the game run faster.

A stronger option is real ES modules, joined by a bundler into the same single file. That gives a true map of what depends on what. It also breaks a written rule: "Files in src/sim/ are not ES modules." We do not propose it without your word.

2. Indexes in place of scans

IndexReplacesRule it must keep
Beings by sector, updated when one moves."Look at every being" in threat checks, hunts, and stalking.The index only filters. Loops that draw random numbers still run in beings order.
A number for each connected area of walkable ground.The whole-world search that runs when a near search fails.Renumber when a tile opens or closes: a tree falls, a sapling grows, fire passes.
A separate list for dead people.beings never drops a human, so every scan grows for as long as a world is played.Names, lineage, and corpses still read the dead. The snapshot tables change.

Your notes forbid one path shortcut. A step-by-step heuristic once "walked into dead ends around lakes for weeks." Area numbers are not that. They answer "can I get there at all" before any search starts.

Two shipped games use them. RimWorld's colonists once searched the whole map for a route that did not exist. The fix was to number every connected area, and to skip the search when the two numbers differ. Dwarf Fortress does the same on top of its A* search.

3. Pass the camp as an argument

camp is a global. At the start of each being's turn, updateBeing sets it to that being's camp. About 450 lines in src/sim/ then read it without saying so. That count is every line that names camp alone and does not assign it. The G3 notes already call it "a hidden input of every stride." It blocks a Web Worker, a port, and the day tier alike, because no function says what it reads. The fix touches every file but changes no behaviour. The golden holds or the fix is wrong.

4. A scheduler in place of a visit every tick

Today every living being runs every tick, and only its task work waits for its stride. Plan G5 already describes the replacement: "A queue holds every individual by the time its task ends." A sleeping person then costs nothing for eight hours. At 86,400 ticks a day this matters more than anything else on this page.

Factorio does this with sleeping machines and a list of wake-up requests, applied in a fixed order so that replays still match. RimWorld runs slow-changing things every 250 or 2,000 ticks. The draw order changes, so the golden is blessed again, once.

5. Land that sleeps

The G spec says H "can paint a country into tiles when someone first goes there." Go one step further. A country nobody is in keeps its tiles and runs at the day tier. A country with people in it runs at the tick tier. Minecraft does this by distance from the player. Your rule "the land stays true" fits it: a tile is always a real tile, and only the step size changes.

The save needs the same care. At nine times the area it was 30.3 MB, and the page writes it to the browser every world day. Most of that is lists of tiles per country, including countries that were split and no longer exist.

6. Chronicle lines as records, with the sentence made at the edge

A rule would write { what: 'mauled', who: 12, by: 40 }. The page would turn that into a sentence. The watch list in the G spec needs this anyway. The golden would then compare events, not wording. It is also what makes a later port practical, because the namer and the sentences can stay in JavaScript.

A port: not yet, and then only the path search

WebAssembly is the format that lets a browser run code compiled from Rust or C++. It wins on tight loops over plain numbers, with few calls across the boundary to JavaScript. Most of Hearth's time goes to a different kind of work: reading tables, scoring offers, making objects, building sentences. The one part that fits is path search. It is all integers, it already uses typed arrays, and it is near the top of both profiles.

What three ports and one benchmark study found about WebAssembly
CaseResult
Mozilla moved the hot loop of its source-map parser from JavaScript to Rust.Up to 5.89 times faster. It was a tight loop over numbers, and little data crossed between the two languages.
Figma runs a C++ core as WebAssembly.Load time fell by three times against asm.js, an older way to run compiled code in a browser.
Zaplib bet a company on moving slow JavaScript to Rust bit by bit.A real port "only ended up being 5% faster." They shut down and wrote that "there are usually simpler ways to find performance improvements."
A study ran SPEC, a standard set of test programs, as WebAssembly.45% to 55% slower than native code on average. So the ceiling is lower than "as fast as Rust".

A port cannot match the golden, and should not try

A change inside JavaScript should keep the golden exactly. A port cannot, because some maths gives different last digits in another language. Hold a port to two other tests. It must replay its own log to the same story. Over many seeds, it must agree with the JavaScript core within stated limits. The G spec tests the day tier the same way: "The fine tier is the measure."

Which pieces give the same result in Rust, and which do not
PieceSame result in Rust?
The random generator (mulberry32, 32-bit integer maths)Yes, exactly.
Add, subtract, multiply, divide on doublesYes. WebAssembly fixes all of this except the exact bits of a NaN, the "not a number" result of sums like 0 ÷ 0.
Math.pow, used by rollForNo promise. Even two browsers can differ in the last digit.
Math.round on a negative halfNo. JavaScript rounds −2.5 to −2. Rust rounds it to −3.
Sorting with tiesYes, if the port always uses a stable sort.
Numbers printed inside chronicle textRisky. The golden compares the text.

If we port, port the path search and nothing else

  1. Move what a search reads into typed arrays: ground, feature, fire, and one "can walk" byte per tile. This is JavaScript work and the golden must hold.
  2. Write steps, bfs, and reachable in Rust. They read the same memory, so nothing is copied. They use no floating point, so they can match the JavaScript exactly.
  3. Run both on every soak and stop at the first tick where they differ.
  4. Put the compiled Rust path search inside the HTML as text. WebAssembly.instantiate accepts bytes directly, so the release stays one file.

Do this only if path search is still the top cost after the area numbers are in. It may not be.

Rust is the language we would pick. Its first web tooling group closed in 2025, and new maintainers took over the main tool. Rust also compiles to native code, which a desktop build or Godot could use.

The project already has what a port needs. There is one way in (inject). The whole state saves as plain data, and REFS lists every link between records. A task is a plain record. Every rule reads a table. tests/door.js and the save-load-run-on test in tests/snapshot.js would run against a ported core almost as they are.

No game engine is needed, and each one costs the single file

We weighed game engines for a free and open source project, with the web valued and iPad notable but not critical. Godot is the best of them, and it still does not pay for itself here. Godot cannot run a JavaScript core, so the core would be rewritten in GDScript, which is interpreted, or in Rust. The people who maintain Rust for Godot call its web export "experimental". Either way the single file and the Node tests go.

Other game engines a free project could use

PixiJS is a drawing library, not a game engine, and it keeps the single file. Every game engine below gives it up. Agents write most of this code from a terminal, and a toolchain of plain text files lets them keep doing that.

If a desktop build is wanted

The cheapest route wraps the same HTML file. Tauri 2 is free, MIT or Apache, and builds for Windows, macOS, Linux, iOS, and Android. itch.io hosts HTML games as they are. Steam affects the choice of licence. Valve warns that the Steamworks SDK "is incompatible with some open source licenses." A licence that requires all linked code to be open, such as the GPL, may conflict with it. A permissive one such as MIT does not.

The better long-term shape is one core with more than one front end. Step 3 and step 6 of the model changes lead there whether or not anything is ever ported.

Before that split can happen, the page has to stop reading the core's variables directly. It names the core's saved variables about 380 times today, on about 260 lines, and writes one of them (camp). A Web Worker needs the same separation. GitHub Pages cannot send the headers that shared memory between threads requires, so a worker would exchange messages with the page.

What we do not know

  • How long drawing takes in the browser. Every number here is from Node. The map redraw loops over every surface tile, and it may become the limit before the core does.
  • Clean timings. The machine was busy all evening.
  • Whether the six "should hold" fixes do leave the golden alone. Nobody has run them.
  • What a G4 tick costs. The branch runs every decision every tick on purpose, until its task 3 sets a pace.
  • How much faster a Rust path search would be. We have no measurement, only the pattern from other projects.
  • How big a Godot web download is for a game like this one.

One more thing will move these numbers. How fast beings walk under G4 is still open between you and the hamlet-mythos session. It changes how much path search a day holds, so step 1 should be run again once it is settled.
