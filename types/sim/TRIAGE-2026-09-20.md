## Reproduction note: 114, not 115

The branch was rebased onto `dev` between the original triage and this file. `dev` picked up
`fix-garden-scan` (commit `f47811c`), which rewrote the garden-bush check in `src/sim/recipes.js`
from a whole-map scan to a four-neighbour check. The old scan read `.garden` on a tile twice
(the old lines 69 and 74); the new check reads it once (now line 62). That is one fewer error,
not a change in this triage's method or a dropped row. I confirmed this is the only difference
by running the reconstruction, normalising both error lists (stripping line and column numbers,
since those move with the rebase), and diffing them: the only line that differs is the extra
`recipes.js` garden error, which the old, pre-rebase run had and this run does not. I did not pad
or trim the list to force it back to 115.

## How this list was made

The interfaces in `types/sim/records.d.ts` and the typed `let` in `src/sim/core.js` were built in
one sitting, so there is no commit that captures the moment between typing the shared state and
fixing the 115 errors it found. I reconstructed that moment from `git show` of the two adjacent
commits (`9d57b19`, before typing the shared state, and `4a25703`, HEAD, after both the typing
and the fixes) and a diff between their `records.d.ts`, which shows exactly which fields, and
which optional markers, were added as fixes. I copied HEAD's `records.d.ts` to a scratch file
under `/tmp`, reversed just those additions by pattern match (verified each pattern matched
exactly once), and left HEAD's new interfaces (Cave, Hill, Grove, Sector, GroundItem,
CorpseMarker) in place with only their pre-fix fields, since removing them entirely falls back
to `any` and hides errors, the same trap the first attempt to rebuild this list found. That attempt was made by the session that ran this work, not by the coordinator. It used the pass-two types file and got (88
errors, 8 of them TS2304, instead of 115). I ran `tsc` against HEAD's `src/sim/` with that
scratch file, under a scratch `tsconfig.json` that lives only in `/tmp`, and saved the raw
output. Nothing under this repository's `types/`, `tsconfig.*.json`, or `src/` was used as scratch
space, and the committed `records.d.ts` was not touched.

## Section 2: fields read with no writer anywhere in src/

None found. I checked every one of the roughly 30 distinct property names in the 114 errors by two
methods: `grep -n '\.<field> *=' src/sim/*.js` for a plain assignment, and `grep -n '<field>:' src/sim/*.js`
for an object-literal or `Object.assign`/spread site. Every field had at least one real writer,
cited in the big table below. Two fields are the reverse case, worth naming though they are not
what this section asks for: `Being.body` (settle.js:247) and `Tile.chasm` (settle.js:156) are
written once and, as far as this grep found, never read again anywhere in `src/sim/`. A write with
no reader cannot crash anything; it is dead data, not a bug.
